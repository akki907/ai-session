Single Agent vs Multi-Agent

Single Agent

User
  ↓
Agent
 ├─ Search
 ├─ Code
 ├─ Database
 └─ API

One LLM, many tools. Context grows. Prompts get cluttered.

Multi-Agent

User
  ↓
Supervisor
 ├─ Research Agent
 ├─ Coding Agent
 └─ Doc Agent

Specialized agents with their own context, tools, instructions.

Why Multi-Agent?

Benefits

  • Responsibility separation
  • Specialized tools per agent
  • Specialized instructions per agent
  • Permission boundaries
  • Independent contexts (smaller, focused)
  • Parallel execution

Trade-offs

  • More LLM calls (cost ↑)
  • More latency
  • More state to manage
  • Harder to debug
  • More failure modes
Rule of thumb: start with a single agent. Split when (a) prompts exceed ~3k tokens of instructions, or (b) two distinct permission domains appear.

Planner / Worker

Planner
  ↓
Task 1 → Worker
Task 2 → Worker
Task 3 → Worker
  ↓
Aggregator
  • Planner — decomposes a goal into independent tasks.
  • Worker — one specialist agent per task.
  • Aggregator — combines the results into a final answer.
Best for: research tasks where each subtopic is independent.

Supervisor

            Supervisor
          /     |      \
         ↓      ↓       ↓
    Research  Coding  Database
      Agent    Agent     Agent
  • Routes incoming requests to the right specialist.
  • Owns the shared state across agents.
  • Decides when to finish.
LangGraph implements this naturally with conditional edges from a supervisor node.

Reviewer

Worker
  ↓
Output
  ↓
Reviewer
  ↓
 ┌─────────┐
 ↓         ↓
Pass      Fail
 ↓         ↓
End      Retry
  • Validates the worker's output against a rubric.
  • On PASS → end.
  • On FAIL → loop back with reviewer feedback.
Pro tip: use an LLM-as-judge reviewer with a strict schema; never trust the same LLM that produced the output.

Sequential vs Parallel

Sequential

Agent A → Agent B → Agent C

Each stage depends on the previous. Use when the output of A is the input to B.

Parallel (fan-out)

Planner ──┬── Agent B ──┐
          └── Agent C ──┴── Aggregator

Tasks are independent. Use when none of the agents need each other's output.

Latency win: 3 parallel agents ≈ 1 sequential agent (in wall time). Cost stays roughly the same.

Shared State + Communication

Agents communicate through one of:

  • Shared state object — a TypedDict that every node reads/writes (LangGraph default).
  • Messages — agents post to a shared queue.
  • Task results — workers return JSON; planner aggregates.
  • External store — Redis, Postgres, or a vector DB.
{
  "task_id": "research-123",
  "agent": "web-researcher",
  "status": "completed",
  "result": "..."
}
Watch out: shared state grows. Cap it. Summarize. Persist only what's needed.

Failure Handling + Retry

Agent
  ↓
Tool
  ↓
Failure?
 ├── No → Continue
 └── Yes
      ↓
    Retry  (max 3, exponential backoff)
      ↓
    Fallback  (cached value / default)
      ↓
    Human  (last resort)
  • Retry transient failures (timeouts, 5xx, rate limits).
  • Fallback stale cached result, or skip the tool and explain.
  • Human when retries + fallbacks both fail.
Anti-patterns: infinite loops, conflicting agent results, agents that hallucinate success.

What you'll build today — a 3-agent research system: Planner fans out to Web/GitHub/Docs, results aggregate, Reviewer validates.

Hands-on — Build a Planner / Worker / Reviewer

  1. Define the shared state (TypedDict) with question, findings, review, answer.
  2. Implement a Planner node that decomposes the question into 3 sub-questions.
  3. Implement 3 Worker nodes (web, github, docs) running in parallel.
  4. Wire the parallel edges from Planner → workers → Aggregator.
  5. Add a Reviewer node. On NEEDS_WORK, loop back to Aggregator with feedback.
