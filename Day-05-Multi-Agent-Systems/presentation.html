Why Multi-Agent?

Benefits

  • Responsibility separation
  • Specialized tools per agent
  • Specialized instructions per agent
  • Permission boundaries
  • Independent contexts (smaller, focused)
  • Parallel execution

Trade-offs

  • More LLM calls (cost ↑)
  • More latency
  • More state to manage
  • Harder to debug
  • More failure modes
Rule of thumb: start with a single agent. Split when (a) prompts exceed ~3k tokens of instructions, or (b) two distinct permission domains appear.

When NOT to Use Multi-Agent

The over-engineering trap: splitting an agent because the pattern looks impressive, not because the task needs it.

Signs you don't need it

  • The task is genuinely sequential end-to-end — no independent subtasks to parallelize or specialize.
  • Instructions + tools fit comfortably in one prompt (well under ~3k tokens).
  • One person/team owns the whole workflow — no real permission boundary to enforce.
  • You're optimizing for a demo, not a debuggable production path.

What it costs you anyway

  • 4-6x the tokens of a single agent for the same task (each hop re-sends context).
  • A failure can now originate in any of N agents — harder to trace than one prompt.
  • More surfaces for silent disagreement between agents — see the anti-patterns slide.
  • Slower to iterate — changing one agent's prompt can shift another agent's behavior.
Rule of thumb: if you can't name the specific permission boundary or parallelizable subtask multi-agent buys you, you probably don't need it yet.

LLM-as-Judge, in Detail

The Reviewer node's most common implementation: a second LLM call that scores the first LLM's output against a rubric — instead of a human or a hand-written rule doing it.

Worker Output
→
Judge Prompt
rubric + output + (optional) reference
→
Judge LLM
Score: 0.9
PASS
Score: 0.4
FAIL + reason

Pros

  • Scales — no human in the loop for every run, works at eval-suite volume.
  • Catches things rules can't: tone, faithfulness to source, reasoning quality.
  • Rubric doubles as documentation of "what good looks like."
  • Cheaper and faster than a human reviewer for routine checks.

Cons

  • Judge inherits the same biases/blind spots as the model class it comes from.
  • Self-preference bias — a judge tends to score outputs from its own model family higher.
  • Position/verbosity bias — can favor the first option shown, or longer answers, regardless of quality.
  • Adds a real LLM call: more cost and latency per review.
  • Its own scores need occasional human spot-checks — it's not ground truth.
Best practice: use a different (often stronger) model as judge than the one being judged, give it a strict output schema (score + reason, not prose), and periodically audit judge verdicts against human review.

Sequential vs Parallel

Sequential

Agent A → Agent B → Agent C

Each stage depends on the previous. Use when the output of A is the input to B.

Parallel (fan-out)

Planner ──┬── Agent B ──┐
          └── Agent C ──┴── Aggregator

Tasks are independent. Use when none of the agents need each other's output.

Latency win: 3 parallel agents ≈ 1 sequential agent (in wall time). Cost stays roughly the same.

Shared State + Communication

Agents communicate through one of:

  • Shared state object — a TypedDict that every node reads/writes (LangGraph default).
  • Messages — agents post to a shared queue.
  • Task results — workers return JSON; planner aggregates.
  • External store — Redis, Postgres, or a vector DB.
{
  "task_id": "research-123",
  "agent": "web-researcher",
  "status": "completed",
  "result": "..."
}
Watch out: shared state grows. Cap it. Summarize. Persist only what's needed.

Memory Across Agents

Shared state (previous slide) lives only for one run. Memory is what survives across runs.

TypeScopeExample
Shared statewhat you just saw One run only — gone when the graph finishes TypedDict passed between Planner → Workers → Aggregator
Short-term memory One conversation / session Message history the agent re-reads each turn
Long-term memory Across sessions, across users of the same agent A Research Agent that recalls findings from last week's run via a vector store
Watch out: long-term memory that isn't scoped (per-user, per-task) leaks context between unrelated runs — treat it like any other shared resource with access boundaries.

Termination & Loop-Guard Conditions

Reviewer loopWorker → Review → Retry
⛔ max_iterations = 3

Guard every loop with:

  • Iteration cap — track a counter in shared state; hard-stop at N (e.g. 3–5).
  • Progress check — if the reviewer's feedback repeats verbatim, stop early — the agent isn't improving.
  • Time / cost budget — wall-clock or token-spend ceiling per run, not just per call.
  • Explicit exit node — every graph loop needs a conditional edge that can say "done," including "gave up."
Anti-pattern: a Supervisor that re-routes to the same agent forever because "PASS" is never satisfied. When the cap is hit, escalate to a human — don't fail silently.

Multi-Agent Anti-Patterns

Ping-pong

Two agents keep deferring back to each other ("ask the other agent") with neither taking ownership — burns iterations without progress. Fix: one agent must own the decision.

Duplicate work

Two workers solve the same subtask because shared state wasn't checked before dispatch. Fix: Planner marks tasks as claimed before fan-out.

Silent disagreement

Two agents return conflicting facts and the Aggregator just picks one without flagging it. Fix: an explicit reconciliation step, or surface the conflict to the reviewer/human.

Hallucinated success

An agent reports "status": "completed" without actually calling the tool or validating the output. Fix: verify claims against tool results, don't trust the agent's self-report.

Common thread: every one of these is a coordination failure, not a reasoning failure — better prompts won't fix them, better state and ownership rules will.

  • Retry transient failures (timeouts, 5xx, rate limits) — with exponential backoff.
  • Fallback stale cached result, or skip the tool and explain.
  • Human when retries + fallbacks both fail.
Multi-agent specific: a failure can cascade — if Worker B depends on Worker A's result, A's fallback value silently becomes B's input. Tag fallback results in shared state so downstream agents (and the Reviewer) know to treat them as lower-confidence.

Evaluating Multi-Agent Systems

The Reviewer checks one run. Evals check whether the system is reliable across many runs.

What to evaluate

  • End-to-end — does the final answer meet the goal? (task success rate)
  • Per-agent — did the Planner produce sane sub-tasks? Did each Worker's output actually get used?
  • Handoff quality — did state passed between agents stay complete and correct?
  • Efficiency — tokens, latency, and iteration count per run, not just correctness.

How

  • Golden test set — a fixed set of inputs with known-good outputs, run on every change.
  • LLM-as-judge — same idea as the Reviewer, but scoring a batch offline against a rubric.
  • Trace review — inspect the full multi-agent trace (spans per agent/tool call), not just the final answer.
  • Regression gate — block a prompt/graph change if eval scores drop.
Why it matters here: multi-agent systems fail in more places than single agents (Planner, each Worker, Aggregator, Reviewer) — evals are how you catch a regression in one agent before it reaches users.

Hands-on — Build a Planner / Worker / Reviewer

  1. Define the shared state (TypedDict) with question, findings, review, answer, and an iteration counter.
  2. Implement a Planner node that decomposes the question into 3 sub-questions.
  3. Implement 3 Worker nodes (web, github, docs) running in parallel.
  4. Wire the parallel edges from Planner → workers → Aggregator.
  5. Add a Reviewer node with a loop guard: on NEEDS_WORK, loop back to Aggregator with feedback, capped at 3 iterations before escalating.
