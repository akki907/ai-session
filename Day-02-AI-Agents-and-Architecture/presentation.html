1. What Is an AI Agent?

An AI agent is an LLM-powered system that can perceive its environment, decide what to do, and act on the world — looping until its goal is met or it hits a limit.

Three defining traits

  • Autonomy — chooses its next action without a human step-by-step prompt.
  • Tool use — calls external functions (search, ticket systems, code, files).
  • Goal-directed — keeps iterating until the goal is satisfied, or it gives up and asks for help.
# Simplified: one LLM call per turn, which returns either
# a final answer or a tool call to make. The loop repeats.
while not done:
    response = llm.call(state)          # model decides: answer, or call a tool
    if response.has_tool_call:
        result = execute(response.tool_call)
        state.append(response, result)   # observation feeds the next turn
    else:
        done = True                       # model chose to answer instead

2. Agent vs Chatbot — a Spectrum, Not a Line

Plain chatbotChatbot + toolsAgent
GoalReply to messagesReply, sometimes with a lookupAchieve a multi-step goal
LoopOne-shot replyReply, maybe one tool callReason → Act → Observe, repeated
InitiativeReactiveReactiveProactive — picks its own next step
Failure modeHallucinates politelyWrong lookup, wrong answerWrong answer and wrong real-world action
Rule of thumb: if it plans several steps ahead and decides when it's done, it's an agent.
Don't reach for an agent by default. If the steps are fixed and known in advance, a plain workflow (or a single tool call) is cheaper, faster, and easier to debug than an autonomous loop.

4a. Tools — The Agent's Hands

A tool is a function the LLM can invoke. Each tool has a name, a description, and a JSON schema of parameters — this is now standardized via MCP (Model Context Protocol), so a tool can be reused across different agents and frameworks.
ToolWhat it does
search_docs(query)RAG search over your knowledge base
get_ticket_status(id)Look up a Jira ticket
create_ticket(title, desc)Open a new Jira ticket
send_email(to, body)Send an email
Rule: descriptions matter more than names — the LLM picks tools based on the description, so write them like documentation, not a variable name.
Tool output is untrusted input. If a tool reads a webpage, a ticket, or a document, treat its result the way you'd treat user input — it can contain instructions trying to hijack the agent ("prompt injection"). Scope each tool's permissions to the minimum it needs.

State vs memory: state disappears when the run ends; memory persists across runs, keyed by a stable thread_id or user_id — never a global variable.

4c. Planning & Reasoning — Deciding What's Next

ReAct (most common)

Reason → Act → Observe, one step at a time. With native tool calling, the model returns a tool call directly — no hand-written "Thought:" text needed.

Plan-and-Execute

Generate a full plan up front, then execute each step. More auditable, less flexible when things change mid-task.

Reasoning techniqueHow
Chain-of-thoughtAsk the model to reason before answering — many current models do this by default
Self-critiqueAsk the model to verify its own answer before finishing
Tree-of-thoughtExplore multiple branches, pick the best one (expensive, rarely needed)
Trade-off: ReAct is flexible but can loop longer. Plan-and-Execute is predictable but rigid if the plan turns out wrong mid-way.

5. Execution Flow — Reason → Act → Observe

User Goal
↓
REASON — model decides: answer, or call a tool
↓
ACT — call get_ticket_status("T-1042")
↓
OBSERVE — result: {"status":"OPEN"}
↓ loop back to REASON
Final Answer — model chooses to stop
Always set a max iteration cap (e.g. 5–10) and a per-run cost/time budget. Without one, a confused agent can loop indefinitely and run up a large bill overnight.

Minimal Tool-Calling Agent (Python)

import json
from openai import OpenAI
client = OpenAI()

SYSTEM = "You are an IT support agent. Use tools when needed, then give a final answer."

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_ticket_status",
        "description": "Look up a Jira ticket by ID.",
        "parameters": {
            "type": "object",
            "properties": {"ticket_id": {"type": "string"}},
            "required": ["ticket_id"]
        }
    }
}]

def get_ticket_status(ticket_id):
    return {"id": ticket_id, "status": "OPEN"}   # stub — replace with a real Jira call

DISPATCH = {"get_ticket_status": get_ticket_status}

def run_agent(user_msg, max_iter=5):
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user",   "content": user_msg}]
    for step in range(max_iter):
        resp = client.chat.completions.create(model="MODEL", messages=messages, tools=TOOLS)
        msg = resp.choices[0].message
        if not msg.tool_calls:
            return msg.content                       # model chose to answer — loop ends
        messages.append(msg)
        for call in msg.tool_calls:
            args = json.loads(call.function.arguments)     # parse, don't just stash the raw string
            result = DISPATCH[call.function.name](**args)
            messages.append({"role": "tool", "tool_call_id": call.id,
                              "content": json.dumps(result)})
    return "(hit max_iter — stopped without a final answer)"
Note: this is native tool calling, the standard way agents work today — there's no hand-written "Thought:" text to parse; the model returns structured tool_calls directly.

Connecting a Real External Tool/API

import json, requests

def get_weather(city: str) -> dict:
    """Look up the current weather in a city."""
    try:
        resp = requests.get("https://wttr.in/" + city,
                             params={"format": "j1"}, timeout=5)
        resp.raise_for_status()
        cur = resp.json()["current_condition"][0]
        return {"city": city, "temp_c": cur["temp_C"],
                "desc": cur["weatherDesc"][0]["value"]}
    except Exception as e:
        return {"error": str(e)}          # wttr.in is flaky — never let a tool crash the loop

TOOLS = [{
    "type": "function",
    "function": {
        "name": "get_weather",
        "description": "Look up the current weather in a city.",
        "parameters": {
            "type": "object",
            "properties": {"city": {"type": "string"}},
            "required": ["city"]
        }
    }
}]
DISPATCH["get_weather"] = get_weather
That's it. A real API call wrapped as a function, with params properly encoded and errors caught — the LLM doesn't know or care whether it's HTTP, a DB query, or a stub.

Hands-on — Build a Simple AI Agent (10 min)

  1. Open code/day2_simple_agent.py and run it — confirm the agent loops with one mock tool.
  2. Add get_weather(city) from the previous slide, backed by a real public API.
  3. Test: "I'm traveling to Tokyo tomorrow — what's the weather?" → agent should call get_weather("Tokyo").
  4. Add a guardrail: any user message containing "password" returns a refusal before the LLM is called. (This is a toy example — a real guardrail needs more than a keyword match.)
  5. Bonus: add a Human-in-the-loop gate on any write-style tool — print "Awaiting approval" and stop before it "executes".
Done? You have a working agent that picks a tool, calls a real external API, handles a failure, and respects a guardrail.

Quick Recap

What's the one-sentence difference between an agent and a chatbot?

An agent plans and takes multiple actions toward a goal and decides for itself when it's done; a chatbot replies once per turn.

Why does a write-style tool need human approval, but a read-only tool usually doesn't?

Reads are safe to retry and don't change anything if the agent is wrong; writes (create, send, delete, charge) can cause real, hard-to-undo damage.

Why treat a tool's output as untrusted input?

If a tool fetches a webpage or document, that content could contain instructions trying to redirect the agent — the same way you'd never blindly trust user-supplied text.

Why does every agent loop need a max iteration cap?

Without one, a confused agent can keep calling tools indefinitely, running up cost and time with no guaranteed exit.
