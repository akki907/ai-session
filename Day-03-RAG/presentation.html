Why RAG?

LLM Alone

  • Trained on public data
  • Knowledge cutoff

LLM + RAG

  • Grounded in your docs

  • Cites sources

Don't skip re-ingestion: hash each source doc; on change, delete its old chunks before re-embedding — otherwise stale and updated chunks both stay in the index, and the agent can retrieve either one.

Chunking Strategies

StrategyHow it worksBest for
Fixed sizeSplit every N chars/tokens, ignoring structureUniform docs, quick baseline
By paragraphSplit on blank linesArticles, blog posts
By sectionSplit on headingsManuals, policies, contracts
SemanticEmbed sentences, split where similarity dropsMixed or unstructured content
Sliding windowFixed size with overlap between chunksLong context, reduces boundary loss

Chunks too small

Precise matches, but each chunk lacks surrounding context — the LLM sees a fragment, not the full idea.

Chunks too large

More context per chunk, but retrieval gets noisy — irrelevant text dilutes the embedding and crowds the prompt.

Rule of thumb: 200–800 tokens per chunk, 10–20% overlap. Always keep source metadata (doc, section, page) attached to the chunk.

Embeddings: Dense vs Sparse

Dense (semantic)

A neural model maps text to a fixed-length vector. Captures meaning — "car" and "automobile" land close together.

text-embedding-3-small/large · Cohere embed-v3 · BGE · E5

Sparse (lexical)

A term-frequency vector — mostly zeros, one weight per vocabulary word. Exact keyword and ID matches win.

BM25 · TF-IDF · SPLADE

ModelDimsNotes
text-embedding-3-small1536Cheap default, strong baseline
text-embedding-3-large3072Higher recall, higher storage cost
bge-large / e5-large1024Open source, self-hosted
Blind spot: dense embeddings can miss exact terms — order IDs, error codes, SKUs — because they're optimized for meaning, not surface form. Hybrid search closes that gap.

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
pairs = [[query, doc] for doc in candidates]
scores = reranker.predict(pairs)
top_docs = [d for _, d in
            sorted(zip(scores, candidates), reverse=True)][:5]
Retrieve broad, rerank narrow. Cheap retrieval casts a wide net for recall; reranking spends compute only on the shortlist for precision — which is why it runs second, not first.

Retrieval Pipeline in Detail

  1. Query understanding — rewrite ambiguous questions, extract filters (date, department, doc type).
  2. Embed the query — keep the raw text too, for the BM25 side.
  3. Hybrid search — vector + BM25 in parallel, fused with RRF.
  4. Metadata filter — apply access control and scope filters before or after search.
  5. Rerank — cross-encoder narrows top-50 to top-5 by true relevance.
  6. Assemble context — dedupe overlapping chunks, order by relevance, fit the token budget.
  7. Generate — LLM answers using only the assembled context, citing sources.
Every earlier slide is a stage here: chunking and embeddings feed steps 1–2, hybrid search is step 3, metadata filtering is step 4, reranking is step 5. Retrieval is a pipeline, not a single call.

Query Decomposition

Step 1 of the retrieval pipeline, zoomed in — for questions no single chunk can answer.

Per-question context

PatternExample
Comparison"Compare X and Y's Q3 revenue" → retrieve X, retrieve Y, compare
Multi-part"What is A, and how does it affect B?" → sub-q for A, sub-q for A's effect on B
Multi-hop"Who manages the person who wrote the Q3 report?" → resolve author → resolve their manager
Not the same as query rewriting. Rewriting turns one vague query into one better query; decomposition turns one query into several independently-retrievable sub-queries, then synthesizes — the mechanism behind multi-hop RAG.

Minimal RAG in 20 Lines

import chromadb
from openai import OpenAI

client = OpenAI()
chroma = chromadb.PersistentClient(path="./db")
col    = chroma.get_or_create_collection("policies")

def ingest(text, meta):
    emb = client.embeddings.create(
        model="text-embedding-3-small",
        input=text).data[0].embedding
    col.add(documents=[text], embeddings=[emb],
            metadatas=[meta], ids=[meta["chunk_id"]])

def ask(q, k=5):
    qe = client.embeddings.create(
        model="text-embedding-3-small", input=q
    ).data[0].embedding
    res = col.query(query_embeddings=[qe], n_results=k)
    ctx = "

".join(res["documents"][0])
    prompt = f"Answer using ONLY:

{ctx}

Q: {q}
A:"
    return client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role":"user","content":prompt}]
    ).choices[0].message.content

Naive RAG

  • One retrieval pass, fixed k
  • No check on result quality
  • Fails silently on multi-hop questions

Agentic RAG

  • Agent decides if, when, and how to retrieve
  • Can rewrite the query, retrieve again, or call other tools
  • Stops once it judges the context sufficient
Same building block, more autonomy. Retrieval stops being a fixed step in a pipeline and becomes a tool the agent's reasoning loop calls — possibly more than once, possibly alongside get_employee or create_ticket — until it decides it has enough grounding to answer.

Beyond Naive RAG: Variants

VariantCore ideaBest for
Naive RAGOne retrieve, one generateBaseline, simple FAQs
Agentic RAGAgent decides if/when/how to retrieve, can loopMulti-step tasks, tool-using agents
Corrective RAG (CRAG)Grades retrieved docs; weak results trigger web search or query rewriteSparse or unreliable knowledge bases
Self-RAGModel critiques its own retrieval and answer, retrieves again if neededHigh-stakes accuracy, self-correction
RAG-FusionGenerates several query variations, retrieves for each, fuses with RRFAmbiguous or under-specified questions
Multi-hop RAGChains retrieval steps — each answer feeds the next queryQuestions needing several linked facts
Graph RAGRetrieves over a knowledge graph of entities and relations, not just similarityRelationship-heavy, multi-hop domains (orgs, supply chains)
HyDELLM drafts a hypothetical answer first, embeds that instead of the raw queryShort or vague queries with poor lexical overlap

Corrective RAG & Graph RAG

Corrective RAG (CRAG)

A lightweight grader scores each retrieved chunk as correct, ambiguous, or incorrect before generation.

Retrieve
↓
Grade relevance
↓ weak → web search / rewrite
Generate

Graph RAG

Documents are first mined into a knowledge graph — entities and their relationships — then retrieval traverses the graph, not just embedding similarity.

Docs → entities + relations
↓
Build knowledge graph
↓ query traverses edges
Multi-hop answer
Why they exist: vector similarity alone can't tell you a retrieved chunk is wrong (CRAG fixes that), or connect facts spread across many documents through relationships rather than wording (Graph RAG fixes that).

Evaluating RAG

Retrieval quality

  • Precision@k — of the top-k chunks, how many are relevant
  • Recall@k — of all relevant chunks, how many made the top-k
  • MRR — how high the first relevant chunk ranks

Generation quality

  • Faithfulness — does the answer stick to retrieved context, no hallucination
  • Answer relevance — does it actually address the question
  • Context precision/recall — did retrieval feed the generator the right chunks, and only those
ToolFocus
RAGASFaithfulness, context precision/recall, answer relevance
TruLensGroundedness, relevance, tracing
DeepEval / LangSmithUnit-test style eval, regression suites
LLM-as-judge: hand-labeling every answer doesn't scale, so most pipelines score faithfulness and relevance with a second, stronger LLM against a rubric — then sample-check that judge against human ratings.
Build a golden set: 30–50 representative Q&A pairs with known-correct sources. Run it on every pipeline change — chunk size, embedding model, reranker — before shipping.
