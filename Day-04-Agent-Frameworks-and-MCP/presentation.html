LangGraph Components, One Level Deeper

State & reducers

State is a TypedDict (or Pydantic model). Fields can carry a reducer via Annotated[list, add] so concurrent nodes merge into a field instead of overwriting it — essential for parallel fan-out.

Command

Command(goto=..., update=...) lets a node update state and choose the next node in one return value — replaces separate conditional-edge functions when the logic lives naturally inside the node.

Send

Send(node, state) dynamically fans a single node out into N parallel invocations with different inputs — the map step of a map-reduce over an unknown-length list.

Subgraphs

A compiled graph can be embedded as a node in a parent graph, with its own state schema — how you compose multi-agent systems out of smaller, independently testable graphs.

Checkpointer

MemorySaver, SqliteSaver, or a Postgres-backed saver persist state after every super-step, keyed by thread_id — this is what makes pause/resume and HITL possible.

Streaming modes

stream_mode="values" streams full state after each step; "updates" streams only the diff; "messages" streams LLM tokens as they're generated.

CrewAI & MCP

CrewAI — Role-Based

  • Agent — role, goal, backstory, tools
  • Task — description, expected output
  • Crew — team + shared process
  • Process — sequential or hierarchical
  • Delegation — agents hand off to peers

MCP — Standard Protocol

  • MCP Client — inside the LLM app
  • MCP Server — exposes tools/resources
  • Tools — functions with schemas
  • Resources — files, DB rows, API data
  • JSON-RPC — wire protocol
  • Streamable HTTP — transport
Why MCP? One standard for any tool — reuse across Claude, GPT, LangGraph, IDEs.

MCP — How a Tool Call Actually Flows

Host app
↔
MCP Client
↔
MCP Server
↔
External system
  1. Discovery — client asks the server for its list of tools/resources; server replies with JSON Schemas describing each one.
  2. Selection — the LLM decides, from the user's request, which tool to call and with what arguments.
  3. Invocation — client sends a JSON-RPC tools/call request over streamable HTTP (or stdio locally).
  4. Execution — the server runs the real logic (hits an API, queries a DB, reads a file) and returns a structured result.
  5. Grounding — the result is appended to the conversation so the model can use it in its final answer.
Tools vs Resources vs Prompts: tools are actions the model can invoke; resources are read-only context the host can attach (a file, a row, a doc); prompts are reusable, server-defined prompt templates the host can surface to the user.

MCP — The Full Primitive Set

Server → Client primitives

  • Tools — invocable functions with a JSON Schema for arguments
  • Resources — addressable, read-only context (URIs like file://, db://)
  • Prompts — parameterized prompt templates the server exposes for reuse

Client → Server primitives

  • Sampling — server asks the client's LLM to complete something, without holding its own API key
  • Roots — client tells the server which directories/URIs it's allowed to operate in
  • Elicitation — server asks the client to collect a missing piece of input from the user mid-call

Transports

TransportUse case
stdioLocal process — server runs on the same machine as the client (most dev/desktop setups)
Streamable HTTPRemote server — supports auth headers, resumable streams, works behind a load balancer
SSE (legacy)Older HTTP transport, being superseded by streamable HTTP
Handshake: every session opens with an initialize request/response where client and server exchange protocol versions and declare which capabilities (tools, resources, sampling, roots) they each support.

A Minimal MCP Server

from mcp.server.fastmcp import FastMCP

mcp = FastMCP("docs-server")

@mcp.tool()
def search_docs(query: str, top_k: int = 5) -> list[dict]:
    """Search internal documentation and return matching chunks."""
    return vector_store.search(query, k=top_k)

@mcp.resource("docs://{doc_id}")
def get_doc(doc_id: str) -> str:
    """Expose a single document as read-only context."""
    return load_document(doc_id)

if __name__ == "__main__":
    # Runs over stdio by default; use mcp.run(transport="streamable-http") for remote
    mcp.run()
Note: the @mcp.tool decorator turns the function's type hints and docstring directly into the JSON Schema the client sees during discovery — no schema to hand-write.

Single Agent or Multi-Agent?

Default to one agent. Split only when a single agent's context, tools, or judgement genuinely can't do the whole job well.

Stay single-agent when

  • The task fits in one clear role and one tool set
  • Steps are short and don't need specialised expertise per step
  • Debuggability matters more than parallelism
  • Latency and cost budgets are tight

Split into multiple agents when

  • Distinct roles need different prompts, tools, or models
  • Sub-tasks can run in parallel (research from 3 sources)
  • You want an independent reviewer/critic step
  • A single context window would get too large or noisy
Common trap: splitting a simple task into agents just because a framework makes it easy — more agents means more latency, more cost, and more places for errors to compound.

Single Agent — Delegation in Motion

There's no delegation here — one agent owns the whole task and loops through it alone.

The same agent thinks, calls tools, and observes results in a loop — "delegation" is just the agent calling itself again.

Multi-Agent — Delegation in Motion

The Planner receives the task, fans it out to specialists in parallel, and the Output assembles once results return.

Three tokens leave the Planner at once and travel independently — that's the parallel fan-out a single agent can't do on its own.

Multi-Agent Topologies

Sequential (pipeline)

Planner → Researcher → Reviewer. Each agent's output is the next one's input. Simple to reason about and debug.

Hierarchical (manager)

A manager/orchestrator agent decomposes the task and delegates to worker agents, then merges their results.

Network (peer-to-peer)

Agents can call each other directly with no fixed order — flexible, but harder to trace and more prone to loops.

How Agents Share Context

Shared state (LangGraph)

All nodes read/write one typed state object. Simple and traceable, but every agent sees the full state — can get noisy at scale.

Message passing (CrewAI tasks)

Each agent only receives what the previous task explicitly outputs. Keeps context focused, but information not passed forward is lost.

Blackboard

A shared, structured store (not just chat history) that any agent can read from or post to — useful when agents work asynchronously.

Direct delegation

One agent calls another agent as if it were a tool, waits for the reply, and continues — good for a manager/worker relationship.

Design question to ask every time: does the next agent need everything so far, or just the distilled result? Passing raw history everywhere is the fastest way to blow your context budget.

Temporal — Durable Execution for Agents

LangGraph and CrewAI orchestrate within a process. Temporal orchestrates across process restarts, deploys, and days — the layer you reach for once an agent workflow has to survive a crash or wait on a human for hours.

Workflow

Deterministic orchestration code — the "what happens in what order." Temporal replays its event history to reconstruct state after any failure, so it must be deterministic.

Activity

The actual side-effecting work — an LLM call, an API request, a DB write. Non-deterministic code (network calls, randomness) always lives in an Activity, never in the Workflow.

Worker

A process that polls a Task Queue and executes Workflow and Activity code. You scale by running more Workers, not by changing the Workflow.

Signals & Queries

Signals push data into a running Workflow (e.g. "human approved step 3"); Queries read a running Workflow's state without changing it.

Durable timers

workflow.sleep(days=3) costs nothing while waiting — no polling, no cron — and survives Worker restarts.

Retry policies

Every Activity gets automatic, configurable retries with backoff — an LLM call or tool call failing transiently doesn't fail the whole agent run.

Temporal — A Durable Agent Loop

from temporalio import workflow, activity
from datetime import timedelta

@activity.defn
async def call_llm(prompt: str) -> str:
    return await llm_client.complete(prompt)  # non-deterministic: lives in an Activity

@activity.defn
async def run_tool(name: str, args: dict) -> dict:
    return await tool_registry[name](**args)

@workflow.defn
class AgentWorkflow:
    @workflow.run
    async def run(self, task: str) -> str:
        plan = await workflow.execute_activity(
            call_llm, task, start_to_close_timeout=timedelta(minutes=2))

        # Durable wait — survives restarts, costs nothing while parked
        await workflow.wait_condition(lambda: self.approved, timeout=timedelta(days=3))

        result = await workflow.execute_activity(
            run_tool, {"name": "search", "args": {"q": plan}},
            start_to_close_timeout=timedelta(minutes=1),
            retry_policy=RetryPolicy(maximum_attempts=3))
        return result

    @workflow.signal
    def approve(self):
        self.approved = True  # a human (or another system) unblocks the wait

Observability — Seeing Inside an Agent Run

A chatbot failure is one bad reply. An agent failure can be a wrong tool call, a bad plan, or a loop that burns budget — you can't fix what you can't see happen, step by step.

Trace
→
Span: plan
→
Span: tool call
→
Span: LLM call
→
Span: final answer

What each span should carry

  • Input and output for that step
  • Latency and token/dollar cost
  • Tool name, arguments, and raw result
  • Model name, temperature, and prompt version

Where it's captured

  • OpenTelemetry — vendor-neutral tracing standard; instruments any framework
  • LangSmith — native tracing for LangChain/LangGraph runs
  • Temporal Web UI — every Workflow's full event history, replayable
  • CrewAI callbacks / step_callback — per-task and per-agent hooks
Ties directly into causal trace analysis: once every step is a span with inputs/outputs, you can trace why a specific downstream failure happened, not just that it happened.

Instrumenting a Tool Call with OpenTelemetry

from opentelemetry import trace

tracer = trace.get_tracer("agent.tools")

@tracer.start_as_current_span("tool_call")
def run_tool(name: str, args: dict) -> dict:
    span = trace.get_current_span()
    span.set_attribute("tool.name", name)
    span.set_attribute("tool.args", str(args))

    result = tool_registry[name](**args)

    span.set_attribute("tool.result_size", len(str(result)))
    return result
Every framework here can emit spans this way — LangGraph nodes, CrewAI tasks, and Temporal Activities can all be wrapped with the same tracer, giving you one unified trace across a mixed stack.

Evaluating Agents — What Does "Good" Mean?

Offline evaluation

  • A fixed golden dataset of tasks with known-good outcomes
  • LLM-as-judge scoring against a rubric for open-ended answers
  • Run before every prompt or framework change — a regression suite for agents

Online evaluation

  • Real production traffic, sampled and scored continuously
  • User feedback (thumbs up/down) fed back into the eval set
  • Alerting on drift in success rate, latency, or cost per run

Core metrics

MetricWhat it catches
Task success rateDid the agent actually accomplish the goal, end to end?
Tool-call accuracyRight tool, right arguments, on the first attempt?
Groundedness / faithfulnessIs the final answer actually supported by retrieved/tool data?
Latency & cost per runIs a "correct" answer arriving too slowly or too expensively to ship?
Trap: optimizing only for one metric (e.g. success rate) while ignoring cost or latency often produces an agent that's "correct" but unusable in production.

A2A — Agent-to-Agent Protocol

MCP standardizes how an agent talks to a tool. A2A (originated at Google, now under the Linux Foundation) standardizes how one agent talks to another agent — including agents built by different teams, on different frameworks, or by different vendors.

Agent Card

A public JSON manifest (like /.well-known/agent.json) describing an agent's identity, capabilities, and how to reach it — how a client agent discovers what a remote agent can do before ever calling it.

Task

The unit of work sent to a remote agent — has a lifecycle (submitted → working → input-required → completed/failed) that both sides track.

Artifacts

The structured output a remote agent produces for a Task — can be streamed incrementally rather than returned only at the end.

Streaming updates

Server-sent events let the calling agent show progress on a long-running remote task instead of blocking silently.

A2A in Action

  1. Discover — client agent fetches the remote agent's Agent Card to learn its capabilities and endpoint.
  2. Delegate — client sends a Task ("summarize this quarter's incidents") with any needed input.
  3. Track — client polls or streams status updates as the Task moves through its lifecycle.
  4. Receive — remote agent returns one or more Artifacts; client incorporates them into its own reasoning.

MCP vs A2A — complementary, not competing

MCPA2A
ConnectsAgent ↔ Tool / data sourceAgent ↔ Agent

In practice: a single system often uses both — MCP for an agent's own tools, A2A when that agent needs to hand off part of the job to an entirely separate agent it doesn't control.

CrewAI — Research Crew

from crewai import Agent, Task, Crew, Process
from crewai_tools import tool

@tool("fake_search")

    return f"Mock findings for {q}"

LangGraph — Parallel + Sequential

from langgraph.graph import StateGraph, START, END
from typing import TypedDict

class S(TypedDict):
    question: str
    web: str; github: str; docs: str
    draft: str; review: str

def web_node(s):    s["web"]    = web_agent(s["question"])
def github_node(s): s["github"] = gh_agent(s["question"])
def docs_node(s):   s["docs"]   = docs_agent(s["question"])
def summarize(s):   s["draft"]  = summarizer(s)
def review(s):      s["review"] = reviewer(s["draft"])

g = StateGraph(S)
g.add_node("web", web_node); g.add_node("github", github_node)
g.add_node("docs", docs_node)
g.add_node("summarize", summarize); g.add_node("review", review)

# Parallel research from START
g.add_edge(START, "web"); g.add_edge(START, "github"); g.add_edge(START, "docs")
g.add_edge(["web", "github", "docs"], "summarize")
g.add_edge("summarize", "review"); g.add_edge("review", END)

Check Your Understanding

When would you reach for LangGraph instead of plain LangChain?

When the workflow needs explicit state, branching, loops, or the ability to pause for human-in-the-loop approval — not just a single prompt-in, answer-out call.

What's the difference between an MCP tool and an MCP resource?

A tool is an action the model can invoke (with side effects); a resource is read-only context the host can attach, like a file or a database row.

Why might a hierarchical topology be safer than a network topology for a new team?

A manager agent keeps a single point of control and a clear audit trail; peer-to-peer delegation is more flexible but easier to get stuck in loops or lose track of who did what.

In today's Research Crew, what would break if the Reviewer ran before the Researcher?

The Reviewer has nothing to check yet — sequential process order matters whenever a later agent's task depends on an earlier agent's output.

Why must Temporal Workflow code be deterministic, while Activity code doesn't need to be?

Temporal recovers from failures by replaying a Workflow's event history — if the Workflow itself called an LLM or the network directly, replay could produce a different result each time. Side effects and non-determinism are pushed into Activities, which Temporal records the outcome of rather than re-running.

An MCP server needs to ask the user "which project?" mid-tool-call. Which primitive handles that?

Elicitation — it lets the server pause and ask the client to collect a specific missing input from the user, rather than guessing or failing.

Your Research Crew's success rate looks great in evals, but production users complain it's slow and expensive. What went wrong with the eval setup?

The eval likely only tracked task success rate and ignored latency and cost per run — a "correct" agent that's too slow or expensive to use has still failed as a product.

Your Planner agent needs to hand a sub-task off to a Reviewer agent that a different team built and deployed separately. MCP or A2A?

A2A — MCP connects an agent to tools and data; A2A is built for one agent delegating a Task to a genuinely separate agent, discovered via its Agent Card.
